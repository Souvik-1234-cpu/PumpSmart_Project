  6. Masked faults: masked channel set to flatline/drift/stuck value
     before fault onset (not simultaneously)
  7. Gradual faults (Label 21): severity starts at 0.05, increases
     monotonically per Paris law rate — no sudden jumps
  8. Physics gates (Step 7) must ALL pass before pkl export

═══════════════════════════════════════════════════════════════════════

⚠️ RULE: Paste text is OUTDATED for architecture after any change.

──────────────────────────────────────────────────────────────────
LEVEL 1 — M4 LSTM-AE (BUILT, LOCKED ✅)
──────────────────────────────────────────────────────────────────

Type               : LSTM Autoencoder
Purpose            : Local 50-step window anomaly detection
Input              : 50 steps × 8 normalized sensor channels
Output per window  : z_t ∈ ℝ⁶⁴  (latent representation)
                     MAE ∈ ℝ⁸   (per-channel reconstruction error)
Threshold          : STATIC = 0.110058 (frozen at M4 commissioning)
Status             : FROZEN — weights never retrained

WHAT LEVEL 1 CAN DETECT:
  ✅ Abrupt single faults (cavitation, sensor dropout, pressure spike)
  ✅ Within-window anomalies visible in any 50-second slice
  ❌ Cannot detect compound chains (resets h₀=0 at every window)
  ❌ Cannot detect gradual drift (50s too short for Paris law slope)
  ❌ Static threshold drifts false-positive over pump lifespan

──────────────────────────────────────────────────────────────────
LEVEL 2 — TCN-AE (PLANNED M8 — NOT YET BUILT)
──────────────────────────────────────────────────────────────────

Type               : 5-layer Dilated Causal Temporal Convolutional
                     Network Autoencoder
Purpose            : Multi-scale temporal reasoning over z_t sequences
                     Detects compound chains, gradual drift, severity
Input              : z_t sequence — shape: (N_windows × 64)
                     where N_windows = sequence_length / 50
                     (e.g. Label 10: 900/50 = 18 windows)
                     NEVER raw sensor data — z_t only (Invariant 16)

ARCHITECTURE:
  Layer | Dilation | Kernel | Receptive Field  | What It Detects
  ------+----------+--------+------------------+------------------
    1   |    1     |   3    |  3 windows=150s  | Local spike pattern
    2   |    2     |   3    |  7 windows=350s  | Short-term anomaly
    3   |    4     |   3    | 15 windows=750s  | Chain transition onset
    4   |    8     |   3    | 31 windows=1550s | Compound chain full span
    5   |   16     |   3    | 63 windows=3150s | Gradual drift + Label 21

Total receptive field : 63 windows = 3,150 raw seconds
Vanishing gradient    : NONE (gradient path = constant 5 layers,
                        not recurrent — no ∏f_t collapse)
Why NOT Transformer   : N_windows = 6–20 too short for attention
                        mechanism to be meaningful at this scale

OUTPUT — THREE SCORES (routing rules are INVARIANT 19):
  score_A : Severity score (mean reconstruction error across z_t seq)
            → feeds Level 4 Rolling Baseline ONLY
  score_B : Drift slope (linear regression gradient of MAE over windows)
            → feeds Level 3 CUSUM ONLY
  score_C : Chain transition score (cross-window pattern correlation)
            → feeds XGBoost M7 as feature ONLY
  ⚠️ NEVER cross-route these scores. Invariant 19.

──────────────────────────────────────────────────────────────────
LEVEL 3 — CUSUM (PLANNED M8 — NOT YET BUILT)
──────────────────────────────────────────────────────────────────

Type               : Cumulative Sum statistical process control
Purpose            : Accumulate slow drift signal to detect gradual
                     faults (Labels 1, 4, 5, 21) before threshold cross
Input              : score_B (drift slope) from Level 2 TCN-AE
Formula            : S_n = max(0, S_(n-1) + score_B - k)
                     where k = allowance parameter (tuned in M8)
Trigger            : S_n > h  (decision threshold h, tuned in M8)
Reset rule         : ONLY on operator acknowledgment OR pump restart
                     NEVER resets on threshold update
Timescale          : Weeks — immune to fast baseline drift

WHY CUSUM IS IMMUNE TO ADAPTIVE THRESHOLD PARADOX:
  The rolling baseline (Level 4) updates θ_t every 50 seconds.
  For Label 21 (bearing_wear_gradual), the fast rolling baseline
  may track the rising vibration as "new normal" — never triggering.
  CUSUM's accumulator is NOT reset by threshold updates.
  It accumulates score_B over weeks until it crosses h.
  Two-speed design: fast (Level 4) suppresses false alarms,
  slow (Level 3 CUSUM) catches the fault regardless.

──────────────────────────────────────────────────────────────────
LEVEL 4 — ROLLING BASELINE (PLANNED M8/M10 — NOT YET BUILT)
──────────────────────────────────────────────────────────────────

Type               : Adaptive threshold engine
Purpose            : Prevent false alarms as pump behavior drifts
                     over months of operation
Input              : score_A (severity) from Level 2 TCN-AE
Formula            : θ_t = μ_rolling(6hr) + 3 × σ_rolling(6hr)
Update frequency   : Every 50 seconds in M10 runtime
Window             : 6-hour rolling window of recent score_A values

CROSSPOINT RISK ADDRESSED:
  Fixed threshold problem: as pump wears normally over months,
  normal score_A rises → fixed threshold generates increasing false
  alarms → operators start ignoring alerts → real fault missed.
  Rolling baseline solution: θ_t follows normal behavior drift.
  False alarm rate stays statistically constant at ~0.3% (3σ rule).

IMPLEMENTATION LOCATION:
  Lives in M10 Flask runtime — NOT in M8 model weights.
  ~20 lines of Python in M10 server-side loop.
  Requires stateful rolling buffer persisted across API requests.

──────────────────────────────────────────────────────────────────
PHYSICS CONTEXT LAYER (PLANNED M10 — NOT YET BUILT)
──────────────────────────────────────────────────────────────────

Purpose            : Every alert must include plain-language physical
                     context — not just label + confidence score.
Location           : Static lookup table inside M10 Flask app
Source             : Physics knowledge — NOT ML inference
Update trigger     : Operator confirmation/rejection (active learning)

MANDATORY FIELDS PER ALERT (ALL 22 CLASSES):
  fault_label              : e.g. "bearing_wear_gradual"
  confidence               : e.g. 0.91 (from XGBoost M7)

SECTION 20: KNOWN LIMITATIONS — REGISTRY + ROADMAP
═══════════════════════════════════════════════════════════════════════

LIM 1 — Static Level 1 Threshold (exists now):
  Current : θ = 0.110058, fixed at M4 commissioning
  Problem : Normal pump wear shifts baseline upward → increasing
            false alarms over months → operator alarm fatigue
  Fix     : M8 Level 4 rolling baseline (not yet built)
  Risk    : If fault develops slowly (Label 21), rolling baseline
            may track it as new normal → missed alert
  Fix²    : Two-speed design — fast rolling (6hr) + slow CUSUM (weeks)

LIM 2 — Synthetic-to-Real Domain Gap:
  Current : All Group B–E sequences physics-synthetic. No real pump
            has run to failure in our dataset.
  Problem : M7 XGBoost may be overconfident. Trained on clean
            synthetic faults, tested on messy real-world ones.
  Fix ST  : Display confidence score + disclaimer in M10 UI
  Fix MT  : Active learning — operator confirms/rejects → real fault
            added to retraining pool over 6–12 months deployment
  Fix LT  : Partner with plant for labelled real fault history

LIM 3 — No Explicit Causal Sensor Ordering:
  Current : All 8 sensors treated equally in feature vector.
            Model cannot explicitly say "Mot.SV rose first, then
            Pres.SV dropped 200s later → bearing caused pressure loss"
  Fix M6.5r: onset_order feature — which channel first exceeded
            0.5σ above baseline and at which window index
  Fix M8  : TCN attention weights (if hybrid) identify which z_t
            windows were most anomalous and which channel drove them

LIM 4 — Single Operating Point / Plant:
  Current : Trained on CIRA (3 pumps, specific installation, piping,
            fluid). M3 normalization config is plant-specific.
  Problem : Deploy on different pump → different NPSHa margin,
            viscosity, ambient → M3 config becomes wrong
  Fix     : M10 commissioning mode (48hr collection → M2+M3 rerun →
            lock new config). M4 weights stay frozen.

LIM 5 — No Remaining Useful Life (RUL) Estimation:
  Current : Detects fault type + severity. No time-to-failure estimate.
  Problem : Maintenance scheduling needs RUL, not just fault label.
  The literature is unambiguous on this. Real pump degradation follows non-linear trajectories:
"Bearing life is generally divided into three stages: normal operation, defect initiation, and accelerated performance degradation. The transition among stages is non-linear — a bearing can spend 95% of its life in Stage I, then collapse to failure in hours once Stage III begins."
And from pump-specific RUL research:
"Degradation-based prognostics require identifying a degradation indicator and crossing a failure threshold, which may be difficult in practice — especially where few degradation trajectories are available — and may introduce further uncertainty and sources of error."
The linear proxy estimated_windows = (S_max - S_n) / r assumes the degradation rate r stays constant. In reality, for a bearing or seal in Stage III:
•	Stage I (normal wear): CUSUM slope r = 0.001/window -> projects 1000 hours
•	Stage II (onset): CUSUM slope r = 0.01/window -> projects 100 hours
•	Stage III (accelerated): CUSUM slope r = 0.1/window -> projects 10 hours
The model using Stage I slope would have told the operator: 1000 hours remaining.
The pump actually fails at Stage III onset which follows Stage II nonlinearly.
Actual remaining time: 10 hours.
The linear estimate was off by 100x.
This is not a modelling error — it is a fundamental physics error.
Decision locked for V15: Linear RUL removed entirely. 
FAULT STAGE: Stage II – Active Degradation Detected
CUSUM Accumulator: S_n = 4.7 (threshold = 8.0)
Drift status: RISING – 3 consecutive windows above rolling baseline
REMAINING USEFUL LIFE: Not estimated.
Pump degradation is non-linear. Any time estimate without run-to-failure data for this specific pump would be unreliable and potentially dangerous. Schedule inspection at earliest maintenance window.
Main motto behind this is - "Power brings responsibility. Responsibility brings duty. If we tell any prediction or outcome it must be valid — that is our duty."

LIM 6 — No Multi-Pump Interaction:
  Current : Single pump monitoring only. No cross-pump signal.
  Problem : In series/parallel plant, Pump A fault changes suction
            head for Pump B. Model misclassifies Pump B's root cause.
  Fix     : Graph neural network architecture — genuine research
            problem, beyond current project scope.
  UI note : "Single-pump monitoring. Cross-pump interactions not
            modelled." (mandatory disclaimer in M10)
